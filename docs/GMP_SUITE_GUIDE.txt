WHAT CHANGES WITH GMP
═══════════════════════════════════════════════════════════════════════

STAGE 1: generate_candidates
  Old: uint64_t candidate (overflows at n > 3×10^9)
  New: GMP mpz_t (unlimited)
  
  Output format: UNCHANGED (still text)
  Speed: SAME (generation is fast regardless)

STAGE 2: filter_primes
  Old: 64-bit Miller-Rabin (12 witnesses)
  New: GMP mpz_probab_prime_p (25 rounds)
  
  Speed: ~50-100x slower, but still reasonable
  Accuracy: Same (negligible error probability)

STAGE 3: check_emirp
  Old: 64-bit Miller-Rabin on reversed numbers
  New: GMP Miller-Rabin
  
  Speed: ~50-100x slower
  Only runs on primes (much fewer candidates)

STAGE 3.5: check_palindrome (NEW!)
  Dedicated otto prime hunter
  Solves n^2 + (n+1)^2 = p using GMP
  Previously combined with other checks

STAGE 4: check_converse
  Old: uint64_t quadratic solver
  New: GMP quadratic solver
  
  Speed: FAST (only runs on emirps, very few)
  Accuracy: BETTER (no overflow issues)

TROUBLESHOOTING
═══════════════════════════════════════════════════════════════════════

Error: "cannot find -lgmp"
  Fix: Install GMP development package
       Fedora: sudo dnf install gmp-devel
       Ubuntu: sudo apt install libgmp-dev

Error: "clock skew detected"
  Fix: touch Makefile
       (Harmless warning, can ignore)

Slow performance in Stage 2
  Expected: GMP is ~50x slower than uint64_t Miller-Rabin
  Solution: Use fewer threads or let it run overnight

Out of memory
  Unlikely with your 64 GB RAM
  If happens: Reduce BUFFER_SIZE in source

Numbers look wrong / overflow
  Check: Are you using ALL GMP stages?
  Fix: Don't mix uint64_t and GMP stages for large numbers
